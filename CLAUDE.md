## Dungeon generation — decided (2026-08-06)

Resolved in a design discussion before starting Milestone 13; this used to be open design question #1. Chosen approach: **hybrid — fixed anchor rooms, procedurally generated middle**, in three layers. Full write-up is in README.md's "Dungeon generation — decided" note; the parts that matter for implementation:

- **Three layers:** hand-authored per-dungeon **template** (room count range, required anchors + ordering, tileset, enemy table, chest count, tile-flags for Act II's frozen chests / fire hazards / flooded corridors) → procedural **room graph** (anchors placed at required graph positions) → procedural **tile layout** (rooms-and-corridors on a grid; anchor rooms use prefab interiors, filler rooms generated).
- **Graph level, not tile-level BSP.** Every constraint that matters — "boss far from entrance", "captive before boss", "all rooms reachable" — is a graph property. Expressing those in tile-space is awkward; in a graph they're trivial. (Note Cory has prior BSP + cellular-automata experience from the separate DungeonMapper project, but caves are deliberately *not* used here — Act I locations are buildings.)
- **Anchors are only entrance / captive / boss**, plus Frank in the starter dungeon. The design doc's gate requirements are *entry* gates on the dungeon door, not internal doors, so gating never constrains layout. Starter dungeon gets its own template shape (extra Frank anchor, shorter, tuned for solo level 1) — a template value, not special-case code.
- **Determinism is forced by save/load, not a nice-to-have.** Milestone 20's suspend save stores mid-dungeon position, so a dungeon must regenerate identically on load. Seed generated on first entry, persisted in the save (one int per dungeon), reused forever after so backtracking finds the same map. New game rolls new seeds — that's the actual replayability mechanism.
- **⚠ Use a dedicated `RandomNumberGenerator` instance per dungeon, never global `randi()`.** The global RNG's state is advanced by every unrelated random call (crit rolls, escape rolls, encounter rolls), so regenerating from a seed via the global RNG would produce a *different* map depending on what else happened in between. This is the single easiest way to break save/load determinism.
- **Collision ended up grid-based, not physics-based — revises what was said during this discussion.** The plan going in was TileSet physics layers (collision "for free" on `set_cell()`). 13a's implementation went a different way once movement was actually looked at: `Player.gd` already moves by setting `position` directly (`move_toward` in `_process()`), never calling `move_and_slide()`/`move_and_collide()`, so CharacterBody2D physics collision was never actually wired to anything — the existing `CollisionShape2D` has been inert since Milestone 1. Rather than switching to real physics (which risks the wall-sliding/corner-catching behavior classic tile-locked RPGs deliberately avoid), 13a added a logical check instead: before moving, `Player._is_walkable()` looks up the destination tile's atlas coordinates directly and blocks the move if it's the wall tile. See the Milestone 13a section below for the full detail. Physics layers may still matter later for non-player collision (props, hazard triggers), but player movement doesn't use them.
- **Split into 13a (tech, hand-built Cathedral) / 13b (generation)** so traversal, collision, doors and dungeon encounters are debugged against a map whose layout is fully known, before randomness is layered on. Follows the existing 8a–8d / 18a–18d convention rather than renumbering the roadmap again.

## Milestone 13a — Dungeon tech (done)

- **`Player` extracted to a reusable scene** (`scenes/player/Player.tscn`: CharacterBody2D + Camera2D + Sprite2D + CollisionShape2D, `Player.gd` attached). Previously the player was embedded directly as a child node inside `Overworld.tscn` — fine when there was only one map, but a second map type (dungeons) made duplicating that node tree the wrong call. `Overworld.tscn` and `CathedralDungeon.tscn` both now instance `Player.tscn` as a child of their own `TileMapLayer`, and `Player.gd` finds its map via `@onready var _tile_map: TileMapLayer = get_parent()` — this only works because every map scene keeps Player parented directly under its `TileMapLayer`; breaking that convention breaks Player.
- **Wall collision is a grid lookup, not physics** (see the revision note above). `WALL_ATLAS_COORDS := Vector2i(1, 0)` — `_is_walkable(world_pos)` converts to a cell via `_tile_map.local_to_map()` and rejects the move if that cell's atlas coords match. Empty/unpainted cells are deliberately treated as walkable (not blocked) — see the Overworld gotcha below for why.
- **Doors/stairs are the same mechanism as walls, one more reserved tile.** `DOOR_ATLAS_COORDS := Vector2i(2, 0)` (new gold tile, see tileset note below). After a move completes, `Player._on_tile_entered()` checks the landed-on cell; if it's a door, it calls `get_door_destination(cell)` on its map's root node (`_tile_map.get_parent()`) instead of running the usual encounter-step check. Each map scene's own script owns its own door-cell → destination-scene mapping (`Overworld.gd.get_door_destination()`, `Dungeon.gd.get_door_destination()`) — `Player.gd` stays generic and never hardcodes a specific dungeon.
- **Placeholder tileset grew a third tile.** `placeholder_tiles.png` is now 48×16 (was 32×16) — column 2 is a gold `(0.85, 0.68, 0.15)` tile for doors/stairs, added via a one-off script using `Image.blit_rect()`, not hand-drawn. Both `Overworld.tscn` and `CathedralDungeon.tscn` register all three atlas coordinates in their own embedded `TileSetAtlasSource` (not yet extracted to a shared `.tres` — each scene has its own copy for now; sharing one resource is a reasonable cleanup whenever the current-content art pass (Milestone 16) replaces the placeholder art anyway, not worth doing twice).
- **`GameManager.current_location` / `current_scene_path`** — each map scene's `_ready()` sets both (e.g. `Dungeon.gd` sets `"cathedral"` / the Cathedral's own scene path). `Battle.gd` reads `current_location` to pick which table out of the new `ENCOUNTER_TABLES` dictionary to roll on (replacing the old hardcoded `ENCOUNTERS` reference in `_generate_encounter()`), and reads `current_scene_path` in both places that used to hardcode `"res://scenes/overworld/Overworld.tscn"` (the post-victory continue prompt and a successful Run/Escape) — so battles fought from inside a dungeon correctly return to the dungeon, not the overworld.
- **Cathedral test room — superseded by 13b.** Originally a fixed 9×7 walled rectangle built via `Dungeon.gd::_build_test_layout()`; that function no longer exists, replaced by `DungeonGenerator.generate()`. Left in the history here for context, not as current behavior — see the Milestone 13b section below for what actually runs now.
- **Cathedral encounter table is stats-only placeholder.** The README describes Fallen Priest (DEF debuff), Cursed Paladin (stun), and Shadow Acolyte (buff allies) — none of that is implementable yet since there's no enemy-ability system at all (`_execute_enemy_turn()` only ever does a plain attack, checked directly during this milestone). `CATHEDRAL_ENCOUNTERS` in `Battle.gd` differentiates the three purely by stats (Paladin = high DEF tank, Priest/Acolyte = lower HP), clearly commented as a stand-in. Full behavior is Milestone 18a's job, once enemy abilities exist as a system — confirmed **not** built by Milestone 14 either (see that section below): boss phases there only change stats/buffs, not behavior, so an enemy-ability dispatch system is still an open need for 18a specifically, not something to assume already exists.
- **⚠ Overworld gotcha found, not fixed:** the Milestone 1 hand-painted Overworld map has **zero wall tiles anywhere** — 259 painted cells, every one of them the floor atlas coordinate. The wall tile was registered in the TileSet but never actually painted onto the map. This means overworld collision is a functional no-op today, purely because of the map's *content*, not the *code* — the same `_is_walkable()` check works correctly the moment a wall tile is actually painted somewhere (proven directly in testing by painting one in). Also discovered: the player's Overworld spawn point sits outside the originally-painted floor patch (in an unpainted/empty region) — harmless today since empty cells are treated as walkable, but worth knowing if that ever changes. Not fixed here since repainting Overworld content is map-content work, not dungeon tech — flagging so it isn't mistaken for new-code behavior later.
- **Battle no longer resets the player to the map's spawn point.** Found during playtesting: every scene reload (including the return from Battle) puts Player at whatever position is baked into that scene file, since `change_scene_to_file()` fully reinstantiates the tree — pre-existing since Milestone 2, just not noticed until dungeon collision made deliberate overworld walking worth doing. Fixed with `GameManager.pending_spawn_position: Vector2` / `has_pending_spawn: bool`: `Player._check_encounter()` stashes its position and sets the flag right before switching to `Battle.tscn`; `Player._ready()` consumes-and-clears it if set, applying it as the spawn position, otherwise falling back to the scene's authored position as before. Applies uniformly to victory, defeat, and successful Run/Escape, since all three return through the same `GameManager.current_scene_path` reload — and to dungeons too, not just the overworld, since the fix lives in the shared `Player.gd`. Door transitions are untouched (`_use_door()` never sets the flag), so walking through a door still lands you at that map's normal fixed entry point, not a stale battle-return position.
- **Verifying scenes headlessly needs a workaround for autoloads.** `godot --headless --script res://foo.gd` does **not** initialize project autoloads (`GameManager` fails to even *compile* as an unresolved identifier in any script loaded that way, including real game scripts like `Overworld.gd` that reference it) — the global-name binding only happens via the normal engine startup path that loads `run/main_scene`. To test scenes that touch `GameManager`, temporarily point `project.godot`'s `run/main_scene` at a throwaway test scene/script, run `--headless --quit`, then restore `project.godot` and delete the throwaway files. This is how 13a's wall/door/encounter-table logic was verified (18 assertions, all passing) before handoff — no test files were committed.

## Milestone 13b — Procedural dungeon generation (done)

Implements the design decided earlier this session (see "Dungeon generation — decided" above). `DungeonGenerator` (`scripts/dungeon/DungeonGenerator.gd`, `class_name DungeonGenerator`, all `static func`s on a `RefCounted`) is pure logic with zero scene/node dependencies — takes a template Dictionary and an int seed, returns a Dictionary describing the layout. This is deliberately a separate script from `Dungeon.gd` (which stays a thin adapter: paint the returned tiles, position the player, own the door-destination lookup) so the generator itself is testable headlessly with no scene instantiation, autoload workarounds, or `TileMapLayer` needed at all — just call `DungeonGenerator.generate(template, seed)` and inspect the returned Dictionary directly.

- **Room graph = a tree on an unbounded slot grid, not tile-level BSP** (matches the earlier design decision's reasoning). `_build_room_graph()` adds one room per step; each new room's parent is chosen only from existing rooms that still have a free cardinal neighbor slot, and it's placed in one of that parent's free directions. This guarantees two things by construction, with no extra bookkeeping needed: **every room is reachable from the root** (it's a tree), and **every parent-child pair is exactly one grid step apart**, which is what makes straight-line corridor carving always safe — a corridor between two adjacent slots can never accidentally pass through a third room, since slots are on a regular grid. `SLOT_SIZE = 10` vs. `room_max_size = Vector2i(7,6)` leaves enough buffer around every room for this to hold.
- **Anchors:** entrance = tree root (depth 0). Boss = whichever room has the greatest depth. Captive = the midpoint of the entrance→boss path if that path has an intermediate room (`path_to_boss[path_to_boss.size() / 2]`), otherwise any other room not on that path — always exists since `min_rooms = 5` guarantees spares. This directly satisfies "captive before boss" as literally as possible: captive sits *on the route to the boss* whenever the tree shape allows it.
- **Tile layout:** each room gets a random size within the template's range, centered in its slot's bounding box. Corridors between parent/child room centers are carved as one L-shaped bend (horizontal segment then vertical). The wall shell is then added in one pass — `_add_wall_shell()` just marks any cell touching a floor cell (8-directionally) that isn't itself floor as a wall — rather than tracking wall placement per room/corridor individually.
- **Entrance and boss rooms both get a door tile** (same dual-exit pattern 13a established — either one leads back to the overworld). **Captive room gets a new 4th placeholder tile** (violet, `CAPTIVE_COORDS := Vector2i(3, 0)` — tileset is now 64×16) marking its center cell, purely for testability/visual confirmation that anchor placement looks reasonable in-editor; there's no rescue mechanic to attach to it yet (that's Milestone 18a).
- **Seeding.** `GameManager.get_dungeon_seed(location)` lazily rolls a seed via the *global* `randi()` the first time a location is visited, then caches it in `GameManager.dungeon_seeds: Dictionary`. This is the one place global randomness is allowed to touch dungeon generation — it's a one-time arbitrary pick, never reused for the generation steps themselves. `DungeonGenerator.generate()` immediately seeds its *own* `RandomNumberGenerator` instance from that value and never touches global `randi()` again, satisfying the determinism requirement from the design decision. `dungeon_seeds` now round-trips through `GameManager.save_game()`/`load_game()` alongside `party`/`inventory` — a small, natural extension of the Milestone 12 save system, not new infrastructure.
- **Player spawn uses a new `Player.snap_to(world_pos)` helper.** `Dungeon._ready()` calls `_player.snap_to(...)` directly after generation completes — safe because `_moving` always starts `false`, so there's no stale-`_target` interpolation risk from repositioning after `_ready()` already ran.
- **⚠ Fixed: battle-return position was getting silently overwritten by the entrance spawn on every dungeon reload.** First playtest: fighting anywhere other than right next to the entrance, then returning from battle, always dropped the player back at the entrance instead of where the fight happened — and made it *look* like other rooms were unreachable, since getting yanked back after every fight meant never walking far enough in one uninterrupted stretch to reach them. Root cause was a `_ready()` ordering bug: `Player._check_encounter()` stashes `GameManager.pending_spawn_position`/`has_pending_spawn` before switching to `Battle.tscn` (this part, from 13a, was fine). But `Player._ready()` (child) runs *before* `Dungeon._ready()` (parent) on every scene reload — so originally, Player would consume-and-clear the pending spawn correctly, and then `Dungeon._ready()` would run right after and unconditionally call `_player.snap_to(generated_entrance_spawn)`, stomping the just-restored position. **Fix:** moved the pending-spawn consumption *out* of `Player._ready()` entirely and into each map controller's own `_ready()` (`Overworld.gd` and `Dungeon.gd` both now check `GameManager.has_pending_spawn` themselves, right where they'd otherwise apply their own default/generated spawn) — since the controller always runs after Player exists as a child, it can make the final, correct call between "restore the battle-return position" and "use my own spawn," instead of Player deciding for itself and then getting overridden. Verified with a 500-seed reachability sweep (confirms the generator itself has no disconnected-room bug — every non-wall cell is always reachable from the entrance) plus targeted tests confirming a stashed mid-dungeon/mid-overworld position survives a full scene reload without being clobbered.
- **Verified headlessly across 200 seeds** (thrown at `DungeonGenerator.generate()` directly, no scene tree needed): room count always within the template's range, entrance/exit/captive cells always distinct and correctly tagged (door/door/captive-marker), player spawn always on a walkable tile, boss and captive always BFS-reachable from the entrance, and the wall shell always fully sealed (every non-wall cell's 4 neighbors are a known tile — no gaps). Also verified same-seed calls produce byte-identical tile dictionaries (`Dictionary.hash()` equality) and that re-entering the Cathedral scene twice reuses the cached seed rather than re-rolling it. No test files were committed — same throwaway-`main_scene` technique as 13a.
- **Known simplification, not yet a problem:** `CATHEDRAL_TEMPLATE` is a single hardcoded `const` on `Dungeon.gd`. Fine with one dungeon; once Milestone 18a adds more, this needs to become per-scene data (a template dictionary keyed by location, or an `@export` on each dungeon scene) rather than a single constant — noted here so it isn't rediscovered as a surprise later.
- **⚠ Fixed: camera was pinning the player to the bottom-right corner of the screen instead of centering them.** Found once dungeon navigation actually depended on seeing your surroundings — the open overworld never made it obvious. `Player.tscn`'s `Camera2D` had `position = Vector2(-160, -90)` (a Milestone 1 leftover), which would be the *correct* way to center a camera whose `anchor_mode` is `ANCHOR_MODE_FIXED_TOP_LEFT` (camera position = view's top-left corner, so offsetting by minus-half-viewport re-centers it on the player). But Godot 4's actual default is `ANCHOR_MODE_DRAG_CENTER` (confirmed via `Camera2D.new().anchor_mode` — value `1`), where the camera's own position directly **is** the view's center, no manual offset needed. With both effects stacked, the view center ended up at `player.position + (-160,-90)` instead of `player.position`, meaning the player rendered in the bottom-right corner of a 320×180 viewport and everything visible extended only up-and-left — confirmed visually by a screenshot showing exactly that. **Fix:** removed the `position` override entirely, letting `Camera2D` default to `Vector2.ZERO` local position (i.e., exactly on the player). Verified headlessly: `Camera2D.global_position == Player.global_position` after the fix. If a camera ever needs `ANCHOR_MODE_FIXED_TOP_LEFT` for some reason in the future, remember the offset math is the *other* way around from what feels intuitive — top-left anchoring needs `-viewport_size/2`, center anchoring (the default) needs `Vector2.ZERO`.
- **⚠ Fixed: bad `TileSetAtlasSource` text caused "Cannot create tile" errors on project reload.** When 13a added the door tile column, its registration was hand-written by copy-pasting the existing 2-column pattern (`N:0/next_alternative_id = 2`, `N:0/0 = 0`, `N:0/1 = 1`) without verifying what that pattern actually meant — it turned out to declare a *second* tile alternative (id 1) that was never really configured, apparently leftover cruft from however tile (0,0) got set up in Milestone 1. 13b's captive-marker column copied the same bad pattern again. Confirmed the divergence by generating a reference `TileSet` through Godot's own `TileSetAtlasSource.create_tile()` API in a throwaway script and diffing the serialized output — the real API only ever emits `N:0/0 = 0`, nothing else, for a plain tile with no alternates. All four columns in both `Overworld.tscn` and `CathedralDungeon.tscn` were cleaned up to match. **Lesson: when hand-editing a Godot resource's text format instead of going through the engine, verify the pattern against what the engine itself actually generates (e.g. build a throwaway resource via script and inspect the saved `.tres`) rather than copy-pasting an existing block on the assumption it's a safe template** — the existing block may itself be carrying accidental/unused state that looks like boilerplate but isn't.

## Milestone 14 — Boss encounters (done)

Builds the generic system the roadmap calls for — "used by both Act I's dungeon bosses (18a-18d) and Act II's kingdom bosses (22b-d)" — validated against one placeholder test boss in the Cathedral, same pattern as 13a/13b's test-tech-first approach.

- **Bosses are visible, fixed encounters, not random ones.** New 5th placeholder tile (crimson, `BOSS_COORDS := Vector2i(4, 0)`, tileset now 80×16) placed by `DungeonGenerator` just inside the boss room's door — reuses the exact same `_offset_within_room()` helper the player's dungeon-entry spawn already used, now shared by both. Walking onto it (`Player._on_tile_entered()` checks `BOSS_ATLAS_COORDS` alongside the existing door check) always starts a fight via `_trigger_boss_battle()` — no step-counter roll, matching the design doc's "Visible on-screen enemies for mini-bosses and main bosses."
- **`Combatant` gained `is_boss`/`boss_phase`/`phase_hp_thresholds`.** `Battle.gd`'s `_generate_encounter()` checks `GameManager.pending_boss_battle` (set by `Player._trigger_boss_battle()`, consumed here) before falling through to the normal random-table path, and builds a single boss `Combatant` from a new `BOSS_ENCOUNTERS` dict (keyed by location, same shape as `ENCOUNTER_TABLES`) instead. Boss fights are always solo — matches "Single enemy with multiple phases for bosses" from the design doc, no group-sizing logic needed.
- **Phase transitions are checked once per boss turn, not the instant a threshold is crossed** — `_check_boss_phase_transition()` runs at the top of `_execute_enemy_turn()` when `enemy.is_boss`, comparing current HP fraction against `phase_hp_thresholds[boss_phase]`. This reads as "the boss recoils, then comes back stronger" rather than interrupting whatever player action just landed the blow, and avoids needing to instrument every single damage-dealing call site in `_do_skill()` — since bosses are always solo, checking once at the start of the boss's own turn is sufficient and centralizes the whole feature in one place.
- **Milestone 14's test boss only changes numbers on phase transition, not what it does** — permanently +6 ATK, and from phase 1 onward its hits also layer a `-4 def_buff` (2 rounds) onto whoever it hits, both reusing existing `Combatant` fields with zero new mechanics. This is a deliberate scope boundary: real per-phase kits (the README's Fallen Guardian switching to "corrupted holy magic" in phase 2, Shadow Lord summoning adds, elemental absorption, etc.) need an actual enemy-ability dispatch system — a parallel to the player's `CLASS_SKILLS`/`_do_skill()` — that doesn't exist yet and isn't part of this milestone. Flagged here so it isn't assumed to already exist when Milestone 18a starts building the Fallen Guardian for real.
- **⚠ Gotcha caught before it shipped:** the phase-transition message was originally being set by `_check_boss_phase_transition()` directly, then *immediately overwritten* a few lines later by whatever outcome message (`hits X for Y`, `dodges`, `misses`, `Sanctuary absorbs`) `_execute_enemy_turn()` sets next — meaning the player would never actually see "enters a new phase!" despite the code technically running correctly. Fixed by having `_check_boss_phase_transition()` return a message-prefix string instead of setting `message_label.text` itself, which every outcome branch in `_execute_enemy_turn()` now prepends to its own message. General lesson: when a function's job is partly "produce a user-visible message" and it's called from inside another function that *also* sets a message afterward, check whether the second assignment silently clobbers the first before assuming the message will actually be seen.
- **Escape is blocked whenever any boss is present** — `_attempt_escape()` checks `_enemies.any(func(e): return e.is_boss)` first and shows "Can't escape from a boss battle!" without rolling, matching "Blocked during boss fights" from the design doc.
- **Boss XP is just a big flat number** (300 for the test boss) — "should always push the party at least one level" from the README doesn't need a formula, just data big enough to satisfy it.
- **Defeated bosses stay defeated.** `GameManager.defeated_bosses: Dictionary` (location → bool) is set on victory in `_end_battle()` and now persists through `save_game()`/`load_game()` alongside `dungeon_seeds` — same small, natural save-system extension pattern as 13b. `Dungeon.gd` checks it while painting tiles and repaints an already-defeated boss's trigger cell as plain floor instead, so there's no way to re-fight (and re-farm XP from) a beaten boss.
- **Verified headlessly:** a 300-seed sweep confirming `boss_trigger_cell` is always distinct from the other three anchors, correctly tagged, and BFS-reachable from the entrance; boss encounter setup (exactly one enemy, `is_boss` set, correct name/stats, starts at phase 0, `pending_boss_battle` consumed); escape lockout firing in a boss battle and *not* firing in a normal one; phase transition (ATK increase, debuff application on the very next hit, and that a second call past the only configured threshold doesn't re-trigger either effect); victory setting `defeated_bosses` and that fact surviving a save/load round-trip; and the dungeon correctly repainting a defeated boss's cell as floor on the next load. One test-only artifact hit and understood, not fixed in game code: calling the real `change_scene_to_file()` path from inside another scene's own `_ready()` (only possible in a synthetic test harness, never during real play) throws a benign "parent busy" engine warning — the assertions around it still pass since the flags it checks are set synchronously before that deferred call.

## Milestone 15 — Equipment & gear (done)

Generic system + one real end-to-end test case, same pattern as 13a/13b/14. Cory asked to jump straight to this after Boss encounters (14), skipping the art/music milestones that now come later in the restructured roadmap — equipment doesn't depend on real art existing.

- **`Combatant.equipment: Dictionary`** — 5 fixed keys (`weapon`/`armor`/`helmet`/`gloves`/`accessory`), each holding an item name or `""`. Now round-trips through `to_save_dict()`/`load_save_dict()` alongside everything else.
- **Stat bonuses are applied by direct mutation, not a separate bonus layer.** `Equipment.equip()`/`unequip()` add/subtract straight into the character's own `atk`/`defense`/`int_stat`/`res_stat`/`agi`/`max_hp`/`max_mp` fields (`_apply_stats()`, sign-flipped for unequip). This was a deliberate choice over the alternative (a parallel `equip_atk_bonus` etc. read at every formula site) — direct mutation means every existing combat formula picks up gear for free, the exact same way `level_up()` already flows through everywhere without any formula needing to know equipment exists. `hp`/`mp` are clamped to the new max after any change, same pattern as `level_down()`. Re-equipping into an occupied slot correctly swaps (unequip-then-equip internally) rather than stacking — verified explicitly, since silently double-applying a bonus on re-equip was an easy mistake to make here.
- **Class lock:** `Equipment.can_equip()` checks the item's `class` key against `member.char_class`; `""` means universal (accessories only, per the design doc — weapon/armor/helmet/gloves defs always carry a real class). `DEFS` currently has one weapon per class, a couple of universal/basic pieces, and Vael's full 4-piece Holy Guardian Set (`scripts/systems/Equipment.gd`) — placeholder test gear, not real loot, seeded directly into `GameManager.inventory` in `_ready()` since there's no shop/loot system yet to award it through.
- **Full Set Bonus — one real bonus wired up, eleven documented but not built.** `Equipment.has_set_bonus(member, set_id)` checks that `armor`+`helmet`+`gloves`+`accessory` are all equipped and share a `set_id` (weapons are deliberately excluded from sets, matching "Weapons upgrade independently" in the design doc). The only set actually hooked into gameplay is Vael's Holy Guardian Set ("all buff skills last 1 extra round") — `Battle.gd._buff_duration(caster, base_rounds)` checks the bonus and is now called by all 4 of Vael's buff skills (Guard, Fortify, Divine Shield, Battle Hymn) instead of hardcoding `2`. The other 11 sets in the README (3 per class × 4 classes) each change a different specific skill's behavior and are real content work with no mechanism to award them yet — add each one as its own `SET_BONUSES` entry + the matching hook in whatever skill it modifies, same pattern as this one, when Act I/II content actually needs it.
- **New equip screen — the game's first overworld-accessible UI.** `scenes/equip/Equip.tscn` + `scripts/equip/Equip.gd`: character select → slot list (shows currently equipped item or `-- empty --`, plus current stats and a Holy Guardian Set indicator when active) → item picker (inventory items filtered by slot+class via `Equipment.equippable_items_for()`, plus an "Unequip" option when the slot is occupied). Same visual conventions as Battle's menus (Label-based, `> `-prefixed cursor, dark background, small font sizes) and the same `ui_up`/`ui_down`/`ui_accept`/`ui_cancel` input pattern, generalized into one `_handle_list_input(count, on_confirm: Callable, on_cancel: Callable)` shared by all three screens instead of writing the up/down/accept/cancel block three times.
- **Opened with `E`, wired into `Player.gd` (not `Overworld.gd`/`Dungeon.gd`).** Since Player.gd is already shared between every map scene, this works from both the overworld and dungeons for free, same reasoning as the boss/door tile detection. Stashes `GameManager.pending_spawn_position`/`has_pending_spawn` before transitioning, exactly like the battle/boss-encounter triggers, so returning from the equip screen lands you back where you opened it rather than at the map's default spawn.

Formation, Inventory, and Party-status screens don't exist yet either — building a whole tabbed menu shell now to hold just one working tab would be scope creep. `E` is a single-purpose key straight to the one screen that exists; a real unified menu is a natural fit for Milestone 17 (UI/UX polish) or whenever enough of these standalone screens accumulate that consolidating them actually pays off.
- **Verified headlessly (37 checks):** equip/unequip stat math including that re-equipping into an occupied slot swaps rather than stacks; class-lock rejection leaves stats/inventory untouched; universal accessories work for any class; set-bonus detection at each of the 4 pieces (absent with 0-3 equipped, present at 4, drops immediately if any one is removed); the buff-duration bonus actually changes `Battle.gd`'s behavior end-to-end and doesn't leak to a different character; `equippable_items_for()` filtering by slot/class/stock; a full save/load round-trip restoring both the `equipment` dict and the gear-inclusive stat values; and the equip screen's complete navigation flow (character → slot → item → equip → back-navigation at each level).
- **⚠ Playtest report, traced but not a code bug — fixed the real gap instead.** First playtest: Cory equipped what he believed was the full Holy Guardian Set on Vael, leveled to 14, cast Guard, and got "2 rounds" instead of 3. Wrote a proper end-to-end integration test this time (the 37 checks above tested `_buff_duration()` and the equip stat math as separate units, never "equip via the real flow, then actually cast Guard through `_do_skill()`, then check the displayed message" — that gap is exactly what let this slip past the first test pass) and it passed clean: the full pipeline — `Equipment.equip()` on `GameManager.party[0]`, a fresh `Battle` instance (confirmed `battle._party[0]` is the *same object*, not a copy), then an actual `_do_skill()` call — correctly produces "3 rounds." So the set-bonus/buff-duration logic itself was never broken. The far more likely real cause: the Equip screen gave **zero feedback on partial set progress** — it only ever announced the bonus once all 4 pieces were already on, with nothing showing "3 of 4" in between. Since "Guardian Emblem" is a universal accessory (no class lock), it's easy to equip it on the wrong character by accident with only 1 copy in inventory — it would just silently vanish from Vael's available items with no explanation. **Fix:** `Equip.gd` now shows live set progress ("Holy Guardian Set: 3/4 equipped") on the stats line whenever at least one piece is on, not just at 4/4, and the item list tags any set piece with its set name in brackets (`Guardian Emblem (x1) [Holy Guardian Set]`) so it's clear which items are meant to go together. Re-verified: progress text correctly reads "3/4" without claiming "active" at 3 pieces, and "4/4 - active" once complete.

## Roadmap restructuring

Two restructuring passes so far, most recent first. **Milestone numbers cited in older entries below are historical** — the roadmap has been renumbered more than once since; the Implementation status table above is always the authoritative current numbering, not any number quoted in the prose here.

### Split Sprites/Music into per-content passes (2026-08-06)

Cory asked what's next after Boss encounters (14), looked at the asset-sourcing sites for the old monolithic Sprites & tiles (15)/Music & sound (16) milestones, didn't find much usable there, and proposed generating art/music per content section as it's written instead of one pass at the end — matching what the *previous* restructuring pass (below) had already flagged as the natural split if this ever came up. Landed as:

- **Old 15 (Sprites & tiles) and 16 (Music & sound) removed as monolithic milestones.** Replaced by three new per-content art/music passes, each placed immediately after the content it covers: **16** (new) — current-content pass, right after Equipment (15), covering everything built so far (Player, Overworld, the Cathedral's generated tileset, current placeholder enemies, Battle UI, baseline BGM/SFX); **19** (new) — Act I pass, right after Act I content (18a-18d); **23** (new) — Act II pass, right after Act II content (22a-22d); **25** (new) — Act III pass, right after Act III + Vorath (24).
- **Equipment (old 18) moved up to 15** — Cory wants it done next, immediately after Boss encounters, ahead of any art work. It still builds with placeholder assets like everything so far; nothing about it depends on real art existing.
- **UI/UX polish (17) kept its relative shape but its dependency changed**: instead of waiting for *all* art/audio in the whole game to exist (impossible to satisfy quickly under the new per-Act art scheme — that wouldn't happen until Act III's pass, near the very end), it now only needs the **current-content pass (16)** to exist — enough real material to design around, not full coverage. Still explicitly excludes Equipment's equip screen and Save/load's slot-picker screen, same as before.
- **Net effect on Act I/II/III content numbers:** Act I content (was 19a-19d) is now **18a-18d**. Act II content (was 22a-22d) keeps its number by coincidence. Act III + Vorath (was 23) is now **24**. Save/load triggers (20) and APK export (21) kept their numbers too, but their position relative to Act I shifted slightly — they now sit after Act I's *art* pass (19) too, not immediately after Act I content itself, so by the time of the APK export checkpoint Act I is actually content-*and*-art complete, not just content-complete.
- **Granularity was a real decision, not assumed:** asked Cory whether art/music milestones should be per-Act (one pass covering all of Act I's 4 dungeons at once) or per-dungeon/kingdom (a separate pass after each individual sub-milestone, e.g. 18a getting its own art step before 18b starts). ## Milestone 8 approach

8 got split into 4 sub-milestones (one per class) because "all class skills" was too big for one pass. Order: **8a Vael → 8b Ryn → 8c Lyra → 8d Silas**, each building on systems the last one introduced.

**Systems already built (reuse these, don't reinvent):**
- Level-gated skills — `CLASS_SKILLS` entries carry `min_level`; skill menu filters by `member.level`
- Buff system — `def_buff`/`atk_buff` + `_rounds` counters on Combatant, ticked in `_tick_buffs()` after each round
- `agi_debuff` + `agi_debuff_rounds` — same pattern, affects turn order sort in `_begin_resolving()`
- Stun — `is_stunned` + `stun_rounds`, checked at top of `_execute_next_turn()`
- Taunt — `taunt_rounds` on the taunting member, checked in `_execute_enemy_turn()`
- Sanctuary — `sanctuary: bool`, consumed on next incoming hit
- Ally targeting — `MenuState.ALLY_TARGETING`, cycles party with up/down, used by any skill with `"target": "ally_choose"`
- Skill menu scrolling — `_skill_scroll`, needed once a class has >5 skills
- AoE handled per-effect-type inline in `_do_skill()` (loop over `_enemies`/`_party` filtered by `is_alive()`)

**8c (Lyra) is done. New systems it added (reuse these too now):**
- Stance tracking — `Combatant.stance: String`, defaults `"Fire"`, persists across battles (same object reference via GameManager, matches design intent: "starts each battle in her last used stance")
- Stance switching — modeled as pseudo-skills in the skill list itself, not a separate menu state. `_open_lyra_skill_menu()` builds `_active_skills` from `LYRA_SKILLS[member.stance]` (level-filtered) plus one `"Switch: X"` entry per other stance (`effect: "switch_stance"`, `cost: 0`, `target: "self"`). No new MenuState or targeting flow needed — `_confirm_skill()`'s existing `"self"` branch already handles it for free.
- Burn DoT — `Combatant.burn_rounds` / `burn_power`, ticked in new `_tick_dot()` (called alongside `_tick_buffs()` in `_execute_next_turn()`'s queue-empty branch). This is the pattern to reuse for Silas's Poison/Bleed in 8d — just add more `*_rounds`/`*_power` field pairs (or genericize into a list of active DoTs if Silas needs 2+ simultaneous DoTs on one target, which Poison+Bleed stacking would require — worth refactoring to an array of `{power, rounds}` dicts before 8d if so, rather than bolting on more named fields).
- Freeze/Paralysis — reuse `is_stunned`/`stun_rounds` directly, no new fields needed
- DoT ticking can now end the battle — `_execute_next_turn()` checks `_enemies`/`_party` alive-emptiness right after `_tick_dot()` and calls `_end_battle()` before falling through to `_begin_selection()`. Any future round-end effect that can deal damage must respect this same check-after-tick order.
- Per-class skill menu builder — Lyra needed a full custom `_open_lyra_skill_menu()` instead of the generic `_open_skill_menu()` path (branched at the top of `_open_skill_menu()` on `char_class == "Lyra"`). If Silas needs something structurally different too (e.g. a stance-like mechanic), follow this same branch-and-delegate pattern rather than overloading the generic path with conditionals.

**Scoping decision — rows are out of scope for now:** Tremor (Lyra, Earth) was designed as row-dependent (front row = single target, back row = AoE reduced) but combat has no front/back row concept at all yet. Scoped Tremor as row-independent single-target for 8c. **This same decision applies to Silas's Vanish, Shadow Strike, Ryn's Ki Blast, and Vael's Divine Shield** — all currently row-independent/unrestricted. Formation & rows is now **Milestone 11** in the roadmap; don't patch in partial row logic for one skill outside that milestone.

**Deferred, not forgotten:** Lyra's Summons (Ignus/Glacius, level 26/35) — a temporary independent front-row combatant that acts on its own for 2-3 rounds. Big enough mechanic (needs its own turn-queue entry, its own AI, row placement) that it was deliberately left out of 8c rather than rushed. Best tackled after Milestone 11 (Formation & Rows), since summons are described as row-placed.

**8d (Silas) is done — Milestone 8 (Class Skills) is now complete for all four classes.** New systems it added:
- Poison DoT (`poison_rounds`/`poison_power`) and Bleed DoT (`bleed_rounds`/`bleed_power`) — separate named field pairs rather than the generic-array refactor floated above, so Poison and Bleed (and Burn) can all be active on the same target simultaneously (Shadowstep applies all three status types plus a stun at once). All three DoTs tick together in `_tick_dot()`.
- Purify now clears poison and bleed too, not just stun — update this again if a 4th status type gets added later.
- Evasion — `evasion_rounds` on the *target*, checked in `_execute_enemy_turn()` before the hit lands (50% dodge chance while active). Vanish sets it to 1 round. At the time of 8d, combat had no row system yet, so Vanish's "move to back row" component was a no-op — **this was completed in Milestone 11**, where Vanish now actually sets `member.row = "back"`. See the Milestone 11 section below.
- Enemy accuracy debuff — `accuracy_debuff_rounds` on the *enemy*, also checked in `_execute_enemy_turn()` (30% chance the debuffed enemy's own attack misses entirely). Smoke Bomb applies it to all enemies for 2 rounds.
- Expose and Death Mark both reuse the negative-`def_buff` debuff pattern from Lyra's Quake (8c) — no new fields needed, just `target.def_buff = -power`.
- `multi_hit` (Ryn's Storm Flurry) now takes an optional `"hits"` key on the skill dict (defaults to 3) so Silas's Flurry could reuse it at 4 hits instead of duplicating the effect handler.
- **Bug fix carried over from 8c:** negative `def_buff` was only ever read in `_execute_enemy_turn()` (enemy attacking the party) — every party-vs-enemy damage formula (`_do_attack`, and the `physical`/`sweep`/`ki_burst`/`multi_hit`/`cripple`/`rising_dragon` effects in `_do_skill()`) ignored `target.def_buff` entirely. This meant Quake's DEF-down debuff had zero actual effect on damage, and would have made Expose/Death Mark equally inert. Fixed by adding `+ target.def_buff` (or `enemy.def_buff`) into all of those formulas. Pure-INT magic effects (`holy`/`fire`/`ice`/`lightning`/`earth` and their variants) don't use defense at all by design, so they're unaffected and unchanged.

## Milestone 9 — Items & Inventory (done)

- Inventory lives on `GameManager.inventory: Dictionary` (item name → count), initialized once in `_ready()` the same way `party` is, persists across battles via the same reference-not-copy mechanism.
- Item definitions live in `Battle.gd`'s `ITEM_DEFS` const, same shape as `CLASS_SKILLS`/`LYRA_SKILLS` entries (`name`, `effect`, `power`, `target`) so they slot into the existing ally-targeting pipeline for free — `_confirm_item()` just calls `_enter_ally_targeting("item_use", item_def)`, identical to how Vael's Guard/Sanctuary/Purify already worked. No new targeting code was needed.
- `_open_item_menu()` filters `ITEM_DEFS` down to whatever has `count > 0` in `GameManager.inventory`, shows `"Potion x10"`-style labels, and falls back to `"No items available."` if the whole inventory is empty (same pattern as the skill menu's `"No skills learned yet."`).
- `_do_item()` decrements the count, dispatches on `effect` (`item_heal`, `item_restore_mp`, `item_cure_poison`) similar to `_do_skill()`'s effect match.
- `_list_scroll` (renamed from `_skill_scroll` — it's shared infrastructure now) and its clamp function `_clamp_list_scroll()` now also apply to `MenuState.ITEM`, not just `MenuState.SKILL`, so the item list will scroll correctly if it ever exceeds 5 entries.
- Starting stock: Potion x10 (50 HP), Elixir x3 (120 HP), Ether x5 (30 MP), Antidote x5 (cures Poison only).
- **Scoping decision:** no "Remedy"/cure-all item. The design doc's Status Effects table scopes Bleed as Purify-only ("antidotes cannot cure it") — a cure-all item would contradict that, so Antidote only touches `poison_rounds`/`poison_power`. If a broader cure item is wanted later, it needs a product decision on whether it's meant to override that Bleed rule, not just an implementation task.
- Not handled: Ether on a target with `max_mp == 0` (e.g. Ryn) silently restores 0 MP with an awkward "Restored 0 MP!" message. Minor, low-priority UX rough edge — player has to know not to Ether Ryn.

## Milestone 10 — Combat formula completion (done)

Closed three gaps found during the post-Milestone-8 docs-vs-code audit:

- **RES stat.** Added `Combatant.res_stat` field + `p_res` param on `_init()` (new last positional arg — `GameManager.gd`'s four `Combatant.new()` calls were updated to pass it) + `"res"` key in `LEVEL_GAINS` for all four classes, using the exact growth values from the README's Growth System table (Vael/Lyra +3 per level, Ryn/Silas +2). `level_up()`/`level_down()` apply it like every other stat. Every magic-classified damage formula in `_do_skill()` now subtracts `target.res_stat` (or `enemy.res_stat` in AoE loops): `holy`/`fire`/`ice`/`lightning`/`earth`, `holy_stun`, `holy_wrath`, `consecrate`, `fire_burn`, `ice_slow`, `ice_freeze`, `ice_freeze_aoe`, `lightning_aoe`, `lightning_paralyze`, `earth_sunder`. Heal formulas (`heal`, `heal_all`) are untouched — resistance doesn't mitigate healing. **Enemies still default to `res_stat = 0`** since `ENCOUNTERS` data in `Battle.gd` was never given RES values (enemies never had INT values either, same gap) — magic still deals full unmitigated damage to current enemies. Revisit if/when enemy balance gets a real pass; not blocking since it's symmetric with how enemies already had no INT/resistance depth before this milestone.
- **Crit system.** `_crit_chance(attacker)` = `min(50, attacker.agi / 4)`, `_roll_crit(attacker)` rolls against it. Applied to **every party-dealt damage instance**, not just physical — the Stats table describes AGI as the crit stat with no physical/magic distinction, so Vael/Lyra's spells crit too, not just Silas/Ryn's strikes. On a crit, damage is doubled and the message gets a `" CRIT!"` tag appended (or folded into the existing status-suffix variable where one already existed, e.g. `" CRIT! Stunned!"`). AoE loops (`sweep`, `consecrate`, `ice_freeze_aoe`, `lightning_aoe`, `earth_sunder`, `toxic_cloud`) roll crit independently per enemy but don't surface a "CRIT!" tag in the AoE summary message — the doubled damage still applies, it's just not called out in text, to avoid a `any_crit`-tracking variable in every single AoE branch. `multi_hit` (Storm Flurry/Flurry) is the one exception that does track `any_crit` across its hit loop and shows the tag, since Flurry's flavor text explicitly says "each hit rolls for crit independently" and that's the one skill where the mechanic is the whole point. **Crit is party-only** — enemies don't roll crits against the party. Revisit if a future boss fight wants that drama.
- **Run/Escape roll.** New `_attempt_escape()`, called from `_confirm_main()`'s Run option instead of an unconditional scene change. Chance = `clampi(50 + roundi((avg_party_agi - avg_enemy_agi) * 2.0), 10, 90)`, comparing average AGI of alive party members vs alive enemies. Success still exits instantly (same UX as before — Run was never a queued/resolved action, it fires immediately during the selection phase); failure shows `"Couldn't escape!"` and returns to the main menu so the character can pick a different action that round (same re-prompt pattern as "Not enough MP!"). Boss-lockout is still a no-op since bosses don't exist yet. **Note:** Run's menu index moved from 4 to 5 in Milestone 11 when Swap Row was inserted before it — see below.
- **Known side effect, not fixed here:** Death Mark and Expose (Silas, 8d) only affect *physical* damage against the marked enemy, since magic formulas read `res_stat`, not `def_buff`. If "increased damage from all sources" is meant literally, Death Mark/Expose would need a second debuff field magic formulas also check — not done, since the design table's exact wording is ambiguous and this wasn't called out as in-scope for 10.

## Milestone 11 — Formation & rows (done)

- **Row field.** `Combatant.row: String`, `"front"` or `"back"`, default `"front"`. `GameManager._ready()` explicitly sets Vael/Ryn to front and Lyra/Silas to back on party creation (matches the README's default formation). Enemies never get a row assigned — `_row_mult()` treats any `is_enemy` combatant as row-neutral, so only the party side of any exchange is ever affected.
- **Swap Row action.** Inserted into the main menu between Defend and Run: `["Attack", "Skill", "Item", "Defend", "Swap Row", "Run"]` — 6 options now. Rather than touching `Battle.tscn` (still only has 5 `Option0`-`Option4` labels), `MenuState.MAIN` was added to the scrollable set alongside `SKILL`/`ITEM` in `_clamp_list_scroll()`/`_update_menu()`, so the existing scroll infrastructure just handles the overflow. **Run's menu index shifted from 4 to 5** — if you're grepping old code/notes for `_menu_cursor` on Run, it's stale. Swap Row is queued (`member.queued_action = "swap_row"`) and resolves in AGI turn order in `_execute_party_turn()`, unlike Run which still fires instantly during selection — this matches the design doc's "costs the character their action for that round" wording, which implies a real action, not a menu shortcut.
- **Row damage multiplier.** `_row_mult(attacker, defender, ranged := false)` returns `0.75` per side that's a non-enemy combatant in the back row (so it can apply twice — back-row attacker hitting a back-row-adjacent effect — though in practice only the party ever has a row, so it's really "0.75 if attacker is back-row party, further ×0.75 if defender is back-row party"). Applied via `dmg = maxi(1, roundi(float(dmg) * _row_mult(...)))`, inserted right after the base damage calc and before the crit roll, in **every** melee-classified formula: `_do_attack`, `_execute_enemy_turn`, and the `physical`/`sweep`/`ki_burst`/`multi_hit`/`cripple`/`rising_dragon`/`poison`/`bleed`/`toxic_cloud`/`shadowstep` effects in `_do_skill()`. Magic formulas (`holy`/`fire`/`ice`/`lightning`/`earth` and all variants) intentionally don't call `_row_mult()` at all — "magic and ranged abilities unaffected" per the design doc.
- **Ki Blast (ranged exception).** Its `CLASS_SKILLS` entry now carries `"ranged": true`. The `"physical"` effect branch reads `skill.get("ranged", false)` and passes it through to `_row_mult()`, which short-circuits to `1.0` when `ranged` is true — full damage regardless of Ryn's row. This is the only skill with the flag; add `"ranged": true` to any future skill that should behave the same way rather than inventing a new mechanism.
- **Shadow Strike (front-row restriction).** New `"row_restrict": "front"` key, checked in `_open_skill_menu()`'s filter alongside the existing level check: `member.row == s["row_restrict"]`. Silently disappears from Silas's skill menu when he's in the back row — same "just don't show it" pattern already used for level-gating, no explicit "can't use this here" message.
- **Vanish (row swap).** Now sets `member.row = "back"` unconditionally in addition to the existing `evasion_rounds = 1`. Idempotent if already in back row.
- **Tremor (row-dependent target/effect).** `_open_lyra_skill_menu()` special-cases Tremor by name: if `member.row == "back"` when the menu opens, it duplicates the skill dict and overrides `name` → `"Tremor (AoE)"`, `effect` → `"earth_aoe"` (new, plain AoE magic damage, no debuff — distinct from Quake's `"earth_sunder"`), `power` → `14` (down from 24, "reduced damage" per design), `target` → `"enemy_all"`. Front row keeps the original single-target `"earth"` effect unchanged. This check happens once when the skill menu is built, not per-cast, so switching rows mid-selection and reopening the skill menu is what updates which version shows.
- **Divine Shield (same-row only).** Changed from buffing `_party` unconditionally to `if ally.is_alive() and ally.row == member.row`. Message updated to name the row instead of saying "Party."
- **UI.** Party HP labels now show a one-letter row tag (`F`/`B`) right after the name, e.g. `"Vael F L5  120/150"`. The turn-selection header spells it out, e.g. `"Vael (Front): 30/30 MP"` — added consistently across the Ryn-Qi, Lyra-stance, generic-MP, and no-MP header variants.
- **Scoped out:** the outside-battle Formation menu (README's controller mapping: "Select: Formation menu, swap rows outside battle"). There's no overworld menu system of any kind yet — `Player.gd` only handles movement — so building a Formation screen now would mean building an overworld menu shell just to hold one option. Row swaps are battle-only for the moment, which still satisfies the in-battle half of the design doc (swapping costs a turn) even though the free outside-battle swap doesn't exist yet.

## Milestone 12 — Save/load core system (done)

- **`Combatant.to_save_dict()` / `load_save_dict(data)`** — serialize/restore progression state only: `level`, `xp`, `xp_to_next`, `hp`/`max_hp`, `mp`/`max_mp`, `qi`/`max_qi`, `atk`, `defense`, `int_stat`, `res_stat`, `agi`, `row`, `stance`, `is_ko` (plus `display_name`/`char_class` written for save-file readability but not read back — party order/identity is fixed, matched by index). Battle-transient fields (buffs, stun, DoTs, evasion, taunt, queued action) are deliberately **not** persisted — they're meant to live only within a single battle. Note: nothing currently clears those fields between battles either (pre-existing gap, not introduced or fixed here) — irrelevant to save/load since a save always happens outside battle.
- **`GameManager.save_game(slot: int)` / `load_game(slot: int)`** — write/read `user://saves/slot_<N>.json` (`SAVE_SLOTS = 3`) via `JSON.stringify()` / `JSON.parse_string()`. Payload is just `{"party": [...], "inventory": {...}}`. `save_exists(slot)` checks a slot without loading it — needed later for a save-slot picker UI.
- **Load mutates in place.** `load_game()` calls `party[i].load_save_dict(...)` on the *existing* `Combatant` objects rather than replacing the array — `Battle.gd` holds `_party = GameManager.party` as a direct reference (see the reference-semantics gotcha below), so replacing the array instead of mutating its contents would silently desync any scene already holding that reference.
- **Debug trigger:** F5 (save slot 1) / F6 (load slot 1), added to `GameManager._input()` rather than `Battle.gd` — GameManager is the one autoload present in every scene, so this works from the overworld too, unlike Battle's F1/F2 which only make sense mid-battle. This is scaffolding for testing only; Milestone 20 replaces it with real triggers (manual save at inns, auto-save after boss/rescue/region-clear, suspend save) and these debug keys should be removed then.
- **Verified via headless test** (Godot `--headless --script`, not committed) that a save/load round-trip correctly restores level, hp, row, and inventory counts after mutating them post-save — no in-editor UI to click yet, so this was the only way to confirm the JSON round-trip works before Milestone 20 wires it to real UI.
- **UI refresh gotcha, fixed:** `load_game()` mutates `Combatant` fields in place, but `Battle.gd`'s HP labels/bars are only redrawn when `_update_ui()` runs, which nothing was triggering on load — first playtest showed loaded state sitting stale on screen until the next action resolved and incidentally called `_update_ui()` itself. Fixed with `GameManager.party_loaded` signal, emitted at the end of a successful `load_game()`; `Battle._ready()` connects it straight to `_update_ui`. Any future screen that displays live party state (an overworld HUD, a save-slot menu) needs to connect to this same signal rather than assuming GameManager mutating data is enough to repaint anything.

## Debug tooling

- **F1** — level up entire party by 1 (Battle.gd `_input()`)
- **F2** — level down entire party by 1
- Capped at `Combatant.MAX_LEVEL = 35`, floored at 1
- Use this to jump to a target level and test newly-unlocked skills without grinding
- **F3** — instantly KO all enemies and win the current battle (`_debug_auto_win()`), granting XP/level-ups the same as a real victory. No-op if the battle is already over. Added during Milestone 13a playtesting to make repeated dungeon-walk/encounter-transition testing fast — without it, every encounter test requires manually fighting to completion.
- **F5** — save party + inventory to slot 1 (GameManager.gd `_input()`, works from any scene)
- **F6** — load slot 1 back into the live party + inventory

## GDScript gotchas hit so far

- Dictionary values return `Variant` — `var x := dict["key"] + 1` fails to infer type. Always `int(dict["key"])` before arithmetic.
- `class_name` makes a script globally accessible without a preload/autoload — used for `Combatant`.
- Control nodes (Label, ProgressBar) parented directly under a Node2D use `position`/`size`, not anchors/containers.
- ProgressBar has a theme-enforced minimum height that ignores `size` — use two `ColorRect`s (bg + fill) instead for thin custom bars.
- `VBoxContainer` + `move_child()` to interleave dynamically-created nodes (e.g. HP bars) between existing scene-defined Labels.
- Autoload singletons live under Project Settings → **Globals** tab in Godot 4 (not "Autoload").
- `Input.is_key_just_pressed()` doesn't exist as a static — use `_input(event)` with `event is InputEventKey and event.pressed and not event.echo` instead.
- GDScript arrays/objects are references — assigning `_party = GameManager.party` means mutations persist automatically, no manual sync needed.
